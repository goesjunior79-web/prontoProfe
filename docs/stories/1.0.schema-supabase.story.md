## Goal

Criar 5 tabelas (`usuarios`, `alunos`, `avaliacoes`, `planejamentos`,
`acessos_dados`) com RLS habilitado, indexes, triggers, storage buckets e
extension pgcrypto. Documentar como rodar migrations.

## Acceptance Criteria

- [x] `supabase/migrations/001_init.sql` cria todas as 5 tabelas
- [x] Tabela `usuarios` criada (não Supabase Auth nativo — REFINO-003)
- [x] Indexes presentes em `user_id`, `aluno_id`, `data`, `capitulo`
- [x] CHECK constraints em `nivel`, `tipo`, `fonte`, `acao`
- [x] FKs com `ON DELETE CASCADE` (alunos→usuarios, etc)
- [x] Triggers de `updated_at` automático
- [x] RLS habilitado em todas as 5 tabelas
- [x] Policies bloqueiam acesso anon/auth (service_role bypassa)
- [x] `supabase/migrations/002_storage.sql` cria buckets `institutional-assets` (public) + `user-assets` (private)
- [x] `supabase/migrations/003_pgcrypto.sql` habilita extension pgcrypto
- [x] `supabase/README.md` documenta como rodar (`supabase db push` ou SQL Editor manual)
- [x] `lib/db/schema.js` exporta constantes JS (TABLES, NIVEIS, TIPOS_PLANEJAMENTO, FONTES_AVALIACAO, ACOES_AUDIT, BUCKETS, RECURSOS_AUDIT)
- [x] Helpers de validação client-side (validateNivel, validateTipoPlanejamento, etc)
- [x] Testes unitários (18 tests) cobrindo as constantes e helpers

## ⚠ Pendência operacional

**Sidney precisa executar as migrations em ambiente real.** Opções:

### Opção A — Supabase CLI
```bash
supabase login
supabase link --project-ref <project-ref>
supabase db push
```

### Opção B — SQL Editor manual no Dashboard
Copia/cola cada migration na ordem 001 → 002 → 003.

Sem isso, o app não pode persistir dados — mas o **código já está pronto** para
quando o ambiente estiver disponível.
