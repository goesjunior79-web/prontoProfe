## Goal

Sincronizar Google profile do NextAuth com tabela `usuarios` do Supabase. Quando
usuária faz login, registro é criado/atualizado e UUID Supabase é propagado pra
`session.user.id`.

## Como funciona

```
[Usuária clica "Login com Google"]
         ↓
[Google OAuth flow completa]
         ↓
[NextAuth: signIn callback]   → return true (autoriza)
         ↓
[NextAuth: jwt callback]      → primeira chamada, account populado
         ↓
   upsertUser({
     googleId: account.providerAccountId,
     email, nome, imagemUrl
   })
         ↓
   Supabase usuarios:
     - SELECT por google_id
     - se existe: UPDATE (ultimo_login = NOW())
     - se não: INSERT
   Retorna { id: 'uuid-supabase', ... }
         ↓
   token.userId = 'uuid-supabase'
   token.googleId = '12345'
         ↓
[NextAuth: session callback]
         ↓
   session.user.id = token.userId       ← UUID Supabase
   session.user.googleId = token.googleId
         ↓
[Endpoints da API consomem session.user.id como user_id]
```

## Endpoints que vão consumir session.user.id

Quando US-005..US-014 forem implementadas, todos os endpoints que persistem
no Supabase vão precisar do user_id:

```js
const session = await getServerSession(req, res, authOptions);
if (!session?.user?.id) return res.status(401)...;

const userId = session.user.id;  // UUID Supabase

await supabase.from('alunos').insert({ user_id: userId, ... });
```

## Tratamento de erro defensivo

Se o Supabase falhar no jwt callback (DB offline, etc.), NextAuth **não bloqueia
o login** — só loga o erro. App opera em modo legado (sem userId Supabase).
Sidney pode investigar pelos logs.

> Trade-off: usuária pode entrar mesmo se DB tá offline, mas operações que
> dependem de userId vão dar erro depois (`session.user.id` undefined).
